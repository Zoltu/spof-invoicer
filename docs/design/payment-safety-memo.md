## Executive Summary

Against the instruction to verify the address over a secondary channel, what this memo recommends is weaker, and the memo states that rather than dressing it up: nothing a page draws is a second channel, because by the time the invoice renders it is the attacker's document and no field in it is signed or authenticated. `[verified in this repository]` — `decodeShare` in `app/ts/invoice/share.ts` and `app/ts/invoice/codec.ts`. The wallet's own window is the closest thing to one, and this page can neither draw it nor check what it says. `[unverified]` — an argument from what a wallet's window renders, not a measurement. **A privacy-preserving double-payment guard (Section 2).** Option 2B is the recommendation, and its record is the one that outlives a reload, a second tab, and a browser restart. `[unverified]` — an argument from what each option's own record survives, and from the reasons Section 2 gives for ruling Options 2A and 2C out, not a measurement.

- One storage key per claimed invoice, named by a SHA-256 digest of that invoice's canonical text, salted with a random value this browser generated and keeps beside it: one claim writes one key, so two tabs claiming two invoices cannot overwrite each other.
- The record holds a version, the claim's place in this browser's own order, and the UTC day the claim expires on, and no address, amount, payee name, invoice id, or invoice text.
- At most 32 records stand once a retention pass has finished, a claim expires on the day 90 days after it was made, the salt is deleted with the last record it salts, and a Forget control in the invoice's document actions clears the record and the salt with it.
- Where storage is blocked or partitioned, the guard keeps today's in-memory latch, opens the panel, and tells the payer the attempt is remembered for this page only, so the protection is never silently dropped.

It lands only with the maintainer's sign-off, because `README.md`'s privacy sentences, the storage sweep, and the runtime blocker all move with it in one step (Section 2, "What Must Change Together").
Estimated effort: two to three days `(estimate)`, plus that gate change and README rewording.

**Blockies, and a local address book (Sections 3 and 4).**

- **Do not ship blockies as a safety measure, and as decoration ship no avatar library.** An avatar is drawn from the address the invoice carries, so it agrees with a substituted address instead of contradicting it, and it fails every payer with low vision or colour-vision deficiency and every payer who has never seen it before. `[unverified]` — an argument from what an avatar would be built from, not a measurement.
  Estimated effort: nothing `(estimate)`, for shipping no library; the vendoring path Section 3 prices at two to four days is what an avatar shipped as decoration alone would cost.
- **Do not build the address book alone.** Build it as the second step of Section 1, on Section 2's storage decision, after the last-paid memory has been in use and its identity rule has been tested against real names; on a shared browser it is a readable list of the people the previous payer paid, worse than Section 2's opaque marker. `[unverified]` — an argument from what the record would hold, not a measurement.
  Estimated effort: five to eight days `(estimate)`, which is Option 1A's three to five days plus the address book's own work on top of that record.

## Scope and Labelling

This memo answers four questions about paying an invoice here: easier address verification, a guard against an accidental double payment, blockies avatars, and a local address book.
Each question carries one recommendation, alongside what that recommendation costs.
Sections 5 to 7 follow those four: a plain-language note on why an address is the length it is, the framing risk the maintainer accepts, and an audit of every label the memo carries.
Every claim carries one of four labels.

- `[verified in this repository]` — read in this repository's code, configuration, or tests; the file is named.
- `[reported from an external source]` — a study, package listing, or vendor statement, cited and not rechecked here.
- `[unverified]` — asserted or plausible, but neither checked here nor cited.
- `[accepted risk]` — a hazard the maintainer has chosen to live with, recorded so it is not read as an oversight.

A proposal, a recommendation, or an effort figure is not a claim and carries no label; a sentence that asserts a fact about this repository, a study, a package, or the world does.
A judgement offered as a preference carries no label either, and a judgement the memo argues for carries `[unverified]`, with the argument written beside it.
Every label closes the claim it marks, and a source the claim does not name in its own sentence follows the label after an em dash.
In a list, the label on the sentence that introduces the list covers its items, and each item still names its own source.
Effort is stated as an `Estimated effort:` line marked `(estimate)`: the maintainer's judgement, not measurements.
No wallet was exercised and no payer was tested for this memo. `[unverified]` — the memo's own account of how it was produced, which nothing in this repository records or can check.

## Glossary

- **ladder** — the ordered list of rungs a value may be set at; the app has two ladders, a screen ladder and a print ladder, and `FIT_RUNGS` in `app/ts/ui/fit-value.ts` is the one statement of both.
- **rung** — one entry in a ladder: on the screen ladder, one font size in one phase, or the residual rung at the screen floor, so one size can be several rungs; on the print ladder, one point size a printed value may be set at, or the wrapping rung, which states no size and lets a value past the floor break.
- **phase** — one of the two row layouts a value is tried in on screen, inline or stacked; each phase's rungs are stated largest first.
- **inline** — the phase that puts the label, the value, and the copy control on one row: the invoice's payment terms draw that row at every width, while a payment panel term draws it above 640px wide and is stacked below that width, where `app.css` gives every panel term a line of its own whatever rung the fitter writes. A panel term's amount and recipient carry a copy control of their own, while its asset name and its network label carry none, being the panel's own readings rather than values a wallet takes.
- **stacked** — the phase that puts the label on a line of its own and gives the value the whole row.
- **residual rung** — the last rung of the screen ladder, taken when no size in either phase holds the value: the value at the screen floor, scrolling its overflow. The cue that the value may be cut off is painted here and in every state no fit has settled — the row a surface has just built, a box the page laid out nothing for, a value the document does not hold yet, a measurement that stopped reporting a width, and a fit that threw — because an engine that paints its scrollbar only once the payer scrolls would otherwise draw a clipped value as if it were whole. A state a fit's own measurement showed whole carries no cue, which is the residue Section 1 records as an accepted risk.
- **wrapping rung** — the last rung of the print ladder, taken when no sized print rung holds the value: its ladder entry states no size, and `print.css` draws it at the print floor, letting the value break rather than shrinking it further.
- **floor** — the smallest size a ladder steps down to.
- **verbatim value** — a value a wallet takes verbatim, drawn as one run the page never truncates or respaces and holds on one line by its font size rather than by wrapping: here the amount, the payee address, and the payment link. On screen no rung breaks one, the value scrolling its overflow inside its own box instead; on paper every print rung lets one break, because a printed page has neither a scroll container nor a copy control to recover a tail, and `app/stylesheets/print.css` states `white-space: pre-wrap` and `overflow-wrap: anywhere` on each sized print rung and on every wrapped segment, with `overflow-wrap: anywhere` on the wrapping rung itself — so a column narrower than the width a rung was priced against continues the value on the next printed line, which is the break Section 1's print rule depends on.
- **print twin** — a second copy of a verbatim value that only the printed page shows.
- **sweep** — a check that scans a set of the repository's files for forbidden patterns; this memo names each sweep for what it scans — the network sweep, the storage sweep, and the vendored sweeps.
- **focus stop** — a stop the payer reaches with the keyboard: the value itself takes focus, is named by its label, and carries its own focus ring.
- **release** — the way to stop everything a surface started: the subscriptions it took and the DOM changes it made, handed back with the element that surface built, so the page can run it when it drops that element, and doing nothing the second time it runs.
- **`releasable`** — the call `app/ts/ui/release.ts` exports that attaches a release to the element it belongs to.
- **`NOTHING_TO_RELEASE`** — the value `app/ts/ui/release.ts` exports for a release that does nothing: the release a surface states when it started nothing, and the subscription `app/ts/app/layout-probe.ts` returns when the engine cannot watch a box.
- **framing** — showing a page inside another page's window: a wallet host frames the invoice so the payer reads it beside the wallet they pay from, and this app permits that framing on purpose (Section 6).
- **opener** — the page that opened a window, which the browser exposes to the opened window as `window.opener`; the payment panel refuses every window that reports one, whatever page that opener names, because presence alone is what the browser reports, and an opener served from the same website is the case that matters, since it can drive the controls of the page it opened (Section 6).
- **avatar** — the small image drawn from a payee address and shown beside it, so a payer who has seen that address's avatar before has something to recognise; this memo treats an avatar as decoration, never as the sole identifier (Section 3).
- **blockies** — the avatar family Section 3 weighs: an image drawn from the address as its seed, as a mirrored grid of cells, which is the shape the libraries weighed there produce.

## 1. Easier Address Verification

### What the App Shows Today

The invoice shows the payee address in full, as text the payer can select, with a control beside it that copies the whole string, and it draws the payment link as a QR code. `[verified in this repository]` — `paymentValue` in `app/ts/ui/payment-section.ts` builds one text node, a copy control, a print twin, and a status for each verbatim term, and `renderPaymentSection` adds `qrBlock` of the view model's `paymentQr`.

The app keeps a value on one line by choosing how large it is drawn, and the choice comes from one of two ladders: the screen ladder the browser measures a value against, and the print ladder the printed page draws a value on. `[verified in this repository]` — the two ladders `FIT_RUNGS` publishes in `app/ts/ui/fit-value.ts`.
The screen ladder lists each phase's rungs from largest to smallest and finishes one phase before it tries the next, so its smallest inline rung, 10px, is tried before the larger stacked rung of 12px, rather than every rung being tried from the largest down. `[verified in this repository]` — the ladder's order in `app/ts/ui/fit-value.ts`, which `smallestFittingRung` walks in that order.
The screen search measures a phase's largest rung once and prices the rungs below it from that measurement, then measures with each rung itself applied every rung it goes on to try: a rung the reading named is measured again before it may be written, so a phase costs one measurement for its largest rung plus one for each rung it steps down to, and a phase whose largest rung holds the value costs one. `[verified in this repository]` — `smallestFittingRung` in `app/ts/ui/fit-value.ts`, beside "a fit measures a phase at its largest rung, then once per rung it steps down to with that rung applied, and only the phases it needs" and "a rung whose own measurement overflows is never written, however the proportional reading priced it" in `tests/fit-value.test.mjs`.
Each ladder has one floor. `[verified in this repository]` — the ladders `FIT_RUNGS` publishes in `app/ts/ui/fit-value.ts`, whose doc comment states each ladder's floor and the order the search walks its phases in, beside "the ladder is searched in two monotone phases and stops at the floor" in `tests/fit-value.test.mjs`; the document's rung rules are in `app/stylesheets/invoice.css`, and the payment panel's in `app/stylesheets/app.css`.

The app takes the first rung that keeps a verbatim value on one line inside the box that holds it, taking the phases in the ladder's own order: the inline row is kept whenever any inline rung at or above the 10px floor holds the value, and the stacked phase is tried only when none does. `[verified in this repository]` — `fitValue` in `app/ts/ui/fit-value.ts`, and the terms `app/ts/ui/presentation.ts` marks `verbatim`.
The payment panel is the one surface where an inline rung is not on the shared row the phase names: below 640px wide `app/stylesheets/app.css` gives every panel term a line of its own whatever rung it carries, so a panel term at that width is stacked either way and its value is fitted against the column the row already gives it. `[verified in this repository]` — the `@media (max-width: 640px)` block at the foot of `app/stylesheets/app.css`, which names `.pay-term`, beside the same width in `app/stylesheets/invoice.css`, which keeps the invoice's own terms on the label's rail.
That is what makes the display safe: a value the payer never sees whole can be checked only against a string that has been shortened. `[unverified]` — an argument about what a whole value buys, not a measurement.

The inline phase steps from 13px down to the screen floor at 10px; the stacked phase steps from 12px down to the same screen floor; and the residual rung holds the value at the screen floor, scrolling, with a line of text beside it — "If the value is cut off, scroll it." — when no rung of either phase holds it. That cue is painted on the row's own cue state rather than on a rung: a surface writes the state as it builds the row, the fitter clears it on the one verdict of its own measurement — a sizing rung that held the value on one line — and the residual rung and every state no measurement settled keep it, whether or not the engine paints the scrollbar (an overlay scrollbar appears only once the payer scrolls). It is worded as an instruction conditioned on the clip rather than as a claim that the value continues, so it reads true beside a cued value that is whole, one no fit has settled, and beside the 311-character address that is genuinely clipped. `[verified in this repository]` — `FIT_CUE_CLASS` and `fitValue` in `app/ts/ui/fit-value.ts`, the cue rules in `app/stylesheets/invoice.css` and `app/stylesheets/app.css`, and "the cue is painted only where a value may be cut off: absent on a value the fit showed whole, and on the rung that scrolls" in `tests/fit-value.test.mjs`.
The cue is kept out of a copied string by `user-select: none`, which is the only exclusion a stylesheet can make, so an engine that serializes generated content into a selection spanning the row can still paste the sentence after the value, and that residual is accepted: the cue sits outside the value's own box and outside every string the app hands a copy control, and its wording is an instruction that reads true beside a whole value as well as beside a clipped one. `[accepted risk]` — the `user-select: none` the cue rules state in `app/stylesheets/invoice.css` and `app/stylesheets/app.css`; no test in this repository can observe a selection or a copied string, because the suites drive a fake DOM with no CSS.
A cue painted only where a fit did not show the value whole leaves one case uncovered, and the memo records it rather than paying for it on every invoice: a value the fit measured whole can still be drawn in a wider face than that measurement priced — a browser minimum font size, `text-size-adjust`, a mobile engine's font boosting, a substituted face — and it is then drawn without the cue. `[accepted risk]` — the cue state `ui/fit-value.ts` clears on its own measurement, beside the doc comment there that states which changes the scale box reports and which it cannot, and ruling a cue under every fitted address, amount, and hash a line a payer learns to discount beside the one value that is genuinely clipped.
The residual row is drawn in the whole-width columns the stacked phase was measured in rather than in the label's rail: it is the one state the row certainly scrolls, so the value is given the widest column the row has and the painted cue is a cue beside it rather than the only thing standing between a clipped value and a payer who reads the prefix as whole. `[verified in this repository]` — the stacked column rules in `app/stylesheets/invoice.css` and `app/stylesheets/app.css`, which name the residual rung beside the stacked ones.

The screen floor exists because below it a monospaced address stops separating `0` from `O` and `l` from `1`. `[verified in this repository]` — the `FIT_RUNGS` doc comment in `app/ts/ui/fit-value.ts`.

Print cannot be measured from script: a printing host lays the document out into its own page box when the payer prints, after the script that drew the page has run, and neither that layout nor the resulting column is something the drawing script can observe. `[reported from an external source]` — the CSS Paged Media specification, whose page box a user agent constructs for the print medium rather than a script for the screen.
So the print twin is sized from its character count against the column it will be printed in: the page's 7in line between the margins, which is 672 CSS pixels, less the payment term's 7rem label rail and its 0.5rem column gap, which is 552 CSS pixels, and an allowance for how wide one printed character can be, set a little wider than a Courier or DejaVu Mono character, so the count holds however wide a substituted face draws. `[verified in this repository]` — the printed value's column width and the 0.62 bound on a character's advance in `app/ts/ui/fit-value.ts`, and "the print ladder's break points follow print.css's own page geometry and the column it leaves a value" in `tests/fit-value.test.mjs`, which derives the same figures from `print.css`'s own `@page` block and `invoice.css`'s own payment term.
The column is the width the twin has because the twin is a block inside that term's value column, and a rung sized against the page's whole line overflows it: an address one rung too large would reach paper as a complete-looking prefix with its tail past the right margin, on a page whose copy control the print path hides. `[verified in this repository]` — the twin's column and the priced width in `app/ts/ui/fit-value.ts`, and the twin's rule in `app/stylesheets/print.css`.
That column is the one a Letter page with these margins draws, not one a printed page is guaranteed to give the twin: a page of another size or a margin changed in the print dialog leaves a narrower column, and script cannot see the page before it prints. `[reported from an external source]` — the CSS Paged Media specification, whose `@page` size and margin a printing host may override.
So the printed presentation is made safe at the stylesheet rather than at the price: a sized rung keeps every character of the value and lets the value continue on the next printed line when the column cannot hold it, so a price taken against a wider column costs paper a visible continuation and never the tail of an address. `[verified in this repository]` — the `white-space: pre-wrap` and `overflow-wrap: anywhere` a sized print rung and every wrapped segment state in `app/stylesheets/print.css`.
Paper needs no cue of its own for that, which is why the on-screen cue that a value may be cut off is scoped to the screen: a printed value is set at a rung the priced column holds, where the column is narrower than that price the value continues on the next printed line, and past the floor's count it is drawn in the segments one printed line of that column holds. `[verified in this repository]` — `printedSegments` in `app/ts/ui/fit-value.ts`, and the rung and segment rules in `app/stylesheets/print.css`.
Every printed line of a payment value is meant to be ruled under, wherever the break falls: each twin holds the value's characters in an inline run, the `.payment-value-print-run` rule puts a dashed `border-bottom` under that run and states no `content`, and it asks the engine for `box-decoration-break: clone` so each rendered fragment of the run takes its own rule. `[verified in this repository]` — the `.payment-value-print-run` rule in `app/stylesheets/print.css`, and "a printed value past the floor's line breaks where the module put it, and every printed line of a value carries the mark at its end" in `tests/fit-value.test.mjs`, which reads that rule and the runs every twin draws — the stylesheet's text and the twin's markup, which is all the evidence here is: no test in this repository prints a page, and none runs an engine.
That the mark reaches a break the page makes inside a run is therefore asked of the engine and not proven here: `box-decoration-break`'s initial value is `slice`, so an engine that does not honour the property draws the run's decoration as one unbroken box and rules only the fragment the box's end lands in, which is the last printed line of that run. `[reported from an external source]` — the CSS Fragmentation Module's definition of `box-decoration-break`, whose `slice` initial value draws a box's decoration as if the box were unbroken, against `clone`, which decorates each fragment.
What the repository does verify is that the value itself still prints complete whatever the engine does with that property: a sized rung keeps every character and lets a value its column cannot hold continue on the next printed line, and a value past the floor prints in the segments `printedSegments` splits it into, so an engine that paints no rule at an interior break costs the payer a continuation cue and never a character of the address. `[verified in this repository]` — the `white-space: pre-wrap` and `overflow-wrap: anywhere` rules a sized print rung and every wrapped segment state in `app/stylesheets/print.css`, and `printedSegments` in `app/ts/ui/fit-value.ts`.
So a printed page whose column is narrower than the priced one, printed by an engine that does not honour `box-decoration-break: clone`, prints an interior line break of an address with no mark at all, and that residual is accepted rather than closed: the rule that marks a printed line is a continuation cue, so what an unmarked break costs is the cue and never a character of the value. `[accepted risk]` — the `box-decoration-break: clone` the `.payment-value-print-run` rule in `app/stylesheets/print.css` asks for, against the `slice` initial value an engine that ignores the property falls back to; no test in this repository prints a page, and none runs an engine, so the marking is asked of the engine rather than proven here.
Where the engine honours `clone`, every ruled line is part of the value, the last one included, and that is what marking a break wherever it falls costs: clone decorates each fragment of a broken inline box alike and can single out none of them, so the rule says "this printed line is the value, in order, with no character between it and the next" rather than "the value continues", and a payer reads a printed value as the whole of its ruled text. `[verified in this repository]` — the `box-decoration-break: clone` the run rule states, and the comment above it in `app/stylesheets/print.css` that states why the last line carries the rule too.

On that geometry 9pt holds up to 74 characters, 8pt 83, 7pt 95, and 6pt 111, so a Sapling address at 78 characters prints at 8pt and a Monero integrated address at 106 prints at 6pt, and only a value past 111 characters — a Zcash unified address, or the `zcash:` link carrying it — reaches the wrapping rung. `[verified in this repository]` — `printFitRung` and `printedCharacters` in `app/ts/ui/fit-value.ts`, with the lengths at "a printed payment value is the whole value, sized by its length and wrapped only past the floor" in `tests/view.test.mjs`.
"Non-breaking everywhere" is therefore met on the screen and not on paper, and the difference is one of what the medium can hold rather than of scope: no screen rung breaks a verbatim value, while a printed page has a fixed column and no scroll container, so a value past 111 characters — the 311-character unified address, and the `zcash:` link carrying it — stays on one line only if it is set below the 6pt floor or compressed sideways. `[unverified]` — this memo's arithmetic and a judgement about legibility: a one-line presentation at that column would need type of about 2.1pt, or a run drawn at about a third of its natural width, and neither is legible on paper.
The wrap that rung states never alters the value: the print twin holds every character of it, in order, with nothing truncated, nothing elided, and no hyphenation or text transform inserted, and the breaks fall where `printedSegments` put them, so the copy a payer takes off the paper carries no space or line break the value does not have. `[verified in this repository]` — `printFitRung` and `printedSegments` in `app/ts/ui/fit-value.ts`, the `white-space: pre-wrap` and `overflow-wrap: anywhere` rules and the run rule in `app/stylesheets/print.css`, and, in `tests/fit-value.test.mjs`, "a printed value past the floor's line breaks where the module put it, and every printed line of a value carries the mark at its end", which holds the segments to the value itself and no rule that draws a twin to hyphenation, an ellipsis, or a text transform.

### What the Evidence Shows

The options below are judged against the instruction to verify the address over a secondary channel. `[unverified]` — an instruction this memo adopts, neither checked here nor cited.

- No published study measures whether an avatar reduces address-substitution losses. `[unverified]` — an absence of evidence, not evidence of absence.
- Forced side-by-side comparison still produced undetected attacks: hex 10.44%, Base32 8.50%, PGP words 8.78%, numeric 6.34%, Peerio words 5.75%, sentences 2.99%, over 1,047 participants. `[reported from an external source]` — Dechand et al., USENIX Security 2016.
- The same study ran a chunk-size experiment: 400 participants, chunk sizes 2 to 8, and chunks of three or four characters were the fastest to compare, with no significant effect on the detection fail rate. `[reported from an external source]` — Dechand et al., USENIX Security 2016.
- Avatars scored well on both accuracy and speed with 436 participants. `[reported from an external source]` — Hsiao et al.
- The further note that comparing avatars is seldom performed in practice is a related-work claim by the later authors, not a finding of the 436-participant study. `[reported from an external source]` — Dechand et al., USENIX Security 2016, reporting on Hsiao et al.
- An avatar therefore helps only where a comparison already happens. `[unverified]` — the two studies above, read together by this memo, not a finding either study states.
- The dominant attack is address poisoning: 270 million attempts, 17.4 million victim addresses, 6,633 successful payoffs, and at least $83.8 million lost on Ethereum and BSC between July 2022 and June 2024. `[reported from an external source]` — Tsuchiya et al., USENIX Security 2025.
- 6,633 payoffs against 270 million attempts is about 0.0025% across both chains, which is this memo's division of two figures the study reports rather than a rate the study states. `[unverified]` — the same study's attempt and payoff counts, divided here.
- The lookalike counts, a figure of 681 typo transfers worth $5.5 million, and a "roughly 0.01% success" rate, all of which appear in secondary coverage of the same study, were not confirmed against the paper and are not relied on here. `[unverified]`
- Their lookalike threshold was at least three matching leading and four matching trailing characters, chosen because that is how interfaces abbreviate addresses on screen. `[reported from an external source]` — same study.
- In June 2026 MetaMask's response to poisoning was detection plus more characters (`0xEdf89FdA047F28…C6341a8ff7ED`), conceding "at a glance, virtually no one catches the difference." `[reported from an external source]` — MetaMask, June 2026.

The uncomfortable pair is the abbreviation and the vendor's conclusion: the characters a payer sees are the attack surface, and the largest wallet vendor's surviving difference is a longer string. `[unverified]` — the two sources above, read together by this memo, not a finding either source states.

## 2. A Privacy-Preserving Double-Payment Guard

### What the Guard Does Today

The guard exists and is deliberately memory-only, so it protects one page session: a reload or a second tab is an ordinary action that defeats it. `[verified in this repository]` — the record of attempted payments in `app/ts/ui/pay.ts` is a module-scope map, and its comment states that the record lives only in memory so a genuine reload starts over.

- The latch that records a send attempt in `app/ts/ui/pay-flow.ts` is set inside the send callback the instant a transaction is handed to the wallet, and cleared only for a wallet rejection of the transaction. `[verified in this repository]`
- A per-invoice map refuses reopening the panel for an invoice already attempted here, through its own lookup of the invoice's key. `[verified in this repository]` — the attempted-payment record and `claimPayment` in `app/ts/ui/pay.ts`.
- The refusal says reloading is the only way to start over. `[verified in this repository]` — the reopen message in `app/ts/ui/pay.ts`, and the send-claimed-elsewhere message in `app/ts/ui/pay-flow.ts`.
- A reload or a second tab wipes the guard, because nothing is written. `[verified in this repository]` — the comment on the attempted-payment record in `app/ts/ui/pay.ts`.
- The app cannot confirm anything on chain: `connect-src 'none'`, and the network sweep in `tests/slow/acceptance.test.mjs`. `[verified in this repository]`
- No runtime file names an API on the storage sweep's own list — `localStorage`, `sessionStorage`, `indexedDB`, `history`, `window.name`, `document.cookie` — which is what the sweep in `tests/slow/acceptance.test.mjs` enforces, and the whole of what it enforces. `[verified in this repository]`

### The Options

**Option 2A — memory plus a channel between tabs only.**
A `BroadcastChannel` would tell other open tabs that an invoice was claimed, and the record would survive neither a reload nor the case that matters most: a payer who reloads because the wallet was unclear, then pays again.
The storage sweep does not name `BroadcastChannel`, so using it would pass the gate silently; the entry must be written deliberately. `[verified in this repository]` — the storage sweep's own list in `tests/slow/acceptance.test.mjs` names only `localStorage`, `sessionStorage`, `indexedDB`, `history`, `window.name`, `document.cookie`.
A channel is scoped to the origin rather than to this page, so every other page that origin serves can join it. `[reported from an external source]` — the HTML Standard's `BroadcastChannel`, whose channels are one group per origin.
This app is served from one origin with a path of its own, and a gateway serves it beside whatever else that gateway hosts, so on a gateway origin the pages that can join the channel are not pages this app wrote. `[verified in this repository]` — `serve.mjs` serves the app's own tree from one origin, and `README.md` records that a shared gateway gives the app an address of its own rather than a website of its own.
What a claim announced there discloses is therefore: to any page on that origin, that somebody claimed an invoice, and the digest of the invoice they claimed. `[unverified]` — a reading of what the announcement would carry, not a measurement.
A page that does not already hold that invoice learns nothing more from the digest, because it is a string the page cannot interpret; a page that does hold the invoice, or can read this browser's storage, already has what it needs to recognise it from the storage record alone, so the channel adds no reach there.
The disclosure is still a disclosure: on a shared origin it tells a page the app did not serve that a payment is under way from this browser, and the pages that can hear it are decided by the gateway's operator rather than by this app.
The mitigation the channel implies, beyond naming it in the storage sweep: announce the salted digest and nothing of the invoice, because the canonical serialization is the invoice itself and a channel is not a private wire; give the channel a fixed name that carries no per-invoice data, so the name cannot become a second statement of what is being paid; and record the origin-scoped disclosure as an accepted risk of adopting the channel at all, so that other pages the gateway serves learning a payment is under way is a decision written down rather than an oversight.
Estimated effort: about a day `(estimate)`.

**Option 2B — one opaque salted hash record in local storage, plus a cross-tab notification.**
One string per invoice would survive a reload, a second tab, a browser restart, and back-and-forward navigation, for as long as the retention rule keeps it.
Its cross-tab notification is the same channel Option 2A weighs, with the same origin scope and the same disclosure of a claim to every page on that origin, so it needs the same mitigation and the same named sweep entry; what the channel carries is the digest, never the record's canonical serialization, and the storage record itself is never announced.
The record's storage reaches further than the channel does, by a different route: `localStorage` is held per origin rather than per page or per path, so every document that origin serves reads the same record, whether or not this app wrote it and whether or not any page of the app is open at the time. `[reported from an external source]` — the Web Storage API in the HTML Standard, whose storage is shared by every document of one origin.
On a shared gateway, where `README.md` states the app has an address of its own and not a website of its own, that means a page served beside the app — one whose operator, not this app, decides what it does — can enumerate the record and read each claim's digest, its place in this browser's order, its expiry day, and the salt in its own key. `[unverified]` — a reading of what the stored lines and the salt's key give such a page, not a measurement.
What that page learns from them is a count and an order rather than an invoice: with no candidate invoice in hand it learns that somebody claimed payments from this browser, how many, and when those claims expire, and with a candidate in hand — the one the gateway already serves — the salt lets it confirm in one hash whether that invoice was claimed here. `[unverified]` — the same reading, stated for each reader in turn.
That is more than the channel discloses, for a plainer reason: a claim announced on the channel is heard only by a page that is open and listening while it is made, while the record sits in storage and is read at any time. `[unverified]` — a comparison of what each path carries, not a measurement.
The mitigation is the requirement `README.md`'s "Open the app" already states and the framing permission of Section 6 already rests on, applied to the record rather than to the fragment: the app's website must be one whose pages are trusted with the invoice. `[verified in this repository]` — the requirement in `README.md`, and the gateway paragraph that states what a shared gateway does and does not give the app.
Nothing short of a server narrows it further, because a page that shares the origin reads that origin's storage by construction. `[unverified]` — an argument from what a shared origin means for every document it serves, not a measurement.
What the record's own shape bounds is how much such a page learns: the record this option describes holds one opaque digest per claim, that claim's place in the order, an expiry day, and the salt, and holds no address, amount, payee name, invoice id, or invoice text.
So the disclosure the record's storage carries is a hazard this memo records rather than one it removes: on a shared gateway the pages that can read the record are decided by the gateway's operator, and the record's shape bounds what they learn without hiding that anything was claimed. `[accepted risk]` — recorded beside the origin-scoped disclosure Option 2A states for the channel, which is the same hazard by a quieter path.
The sign-off must name it together with the channel's, as a requirement of adopting this option rather than a decision already taken. The storage sweep in `tests/slow/acceptance.test.mjs` reads the runtime files for the six API names its own pattern lists and cannot see which pages the serving origin also hosts. `[verified in this repository]`
Estimated effort: two to three days `(estimate)`, plus a gate change and README rewording.

**Option 2C — a fuller record.**
Per-invoice entries with timestamp, status, and optionally payee name and amount: a payment history in everything but name. `[unverified]` — an argument from the fields it would hold, not a measurement.
Estimated effort: four to six days `(estimate)`.

### Recommendation

Option 2B is the recommendation; Options 2A and 2C are not adopted, because 2A would survive neither a reload nor the payer who reloads because the wallet was unclear and then pays again, and 2C is a payment history in everything but name. `[unverified]` — the arguments each option states above.
What follows is exactly what Option 2B would store: the record it would add, not a description of the app — today the attempted payments live only in memory, and none of this storage exists. `[verified in this repository]` — `app/ts/ui/pay.ts`.

Store one storage key per claimed invoice, named by that invoice's own digest, so a claim writes one key of its own:

```
pay-attempt:<hex digest> => <version>:<claim order>:<expiry day>
```

The digest would be SHA-256 over this browser's own salt concatenated with the invoice's canonical serialization, which the guard already uses as its key. `[verified in this repository]` — the key helper in `app/ts/ui/pay.ts` returns that serialization.
The shape is one key per claim rather than one list under one key, and that is what keeps two tabs from rewriting each other's claim: a claim writes the key that names its own invoice and rewrites nothing another tab is also rewriting, so two tabs claiming two different invoices at the same moment cannot overwrite each other's claim — the retention step is what can still cost one, as the concurrency argument below states.
A list under one key could not be made safe that way. `[reported from an external source]` — the Web Storage API in the HTML Standard, which defines `getItem` and `setItem` as separate synchronous calls with no transaction and no compare-and-swap, so a list under one key can be claimed only by read-modify-write, and two tabs interleaving those three steps lose one of the two claims.
Reading a claim is one `getItem` of that invoice's own key, so the refusal is one lookup and cannot be answered from a partly written list.
No new dependency would be needed: `app/ts/util/encoding.ts` already re-exports `sha256`, `utf8ToBytes`, and `toHex`. `[verified in this repository]`

Deliberately not stored: address, amount, payee name, invoice text, invoice id, and any timestamp that identifies a person, the one time value the record holds being the UTC day a claim expires on, which says a claim was made and not when in the day it was made.
The record would hold a version, an opaque digest, that claim's place in the order this browser made its claims in, and the day it expires on, and no address, amount, payee name, invoice id, or invoice text, so the digests alone cannot be read as "who was paid, how much, when": a digest with no candidate invoice beside it names no invoice at all. `[unverified]` — an argument from the fields the record holds, not a measurement.
It does not follow that the record hides when its claims were made or how many there are: a claim expires on the UTC day ninety days after the day it was written, so each record's own value gives back the day of its claim, and a reader that enumerates the record learns how many claims this browser made and the day of each, while a reader holding the salt that sits beside them and a candidate invoice confirms that invoice's payee and amount in one hash. `[unverified]` — the same argument, stated for what the stored value and the salt beside it give a reader who has them.

The salt would be 32 bytes drawn from the platform's cryptographically secure generator, `crypto.getRandomValues`, and kept as lowercase hex in its own key beside the record, in the same storage: every digest the record holds is computed with that one value, so two tabs and a reload of the same browser derive the same digest for the same invoice, which is the determinism the guard needs.
The length and the generator are the whole of what the salt buys, so neither is left to the implementation: 32 bytes is 256 bits, far past the point where guessing the salt is cheaper than guessing the invoice, and `crypto.getRandomValues` is the one generator the platform states as suitable for cryptographic use, while `Math.random` is not, being predictable from its own state. `[reported from an external source]` — the Web Crypto API, whose `getRandomValues` fills its array from the platform's cryptographically secure generator, against the ECMAScript specification's `Math.random`, which promises no unpredictability.
It is persisted rather than chosen per page load for that reason, and it is random rather than compiled into the app for the other: a constant in the app is identical on every install, so anyone holding an invoice link could compute that invoice's digest without having this device at all.

The salt is kept beside the record in the same storage, so it hides nothing from anyone who can read that storage: they hold the salt and the digest together and need only a candidate invoice — the one the link they hold carries — to recompute the digest and confirm it. `[unverified]` — an argument about what one storage key can hide from someone who can read it, not a measurement.
What the salt does buy is narrower, and worth stating exactly: the digest cannot be recomputed off this device by someone holding only a share link, which a constant compiled into the app would allow, and two browsers' records are not comparable with each other without each browser's own salt.
So the record hides which invoice was attempted from someone who sees the record without the salt — a screenshot, an exported or pasted line, a copy separated from the storage it came from — and hides nothing at all from anyone who can read the storage both sit in. `[unverified]` — the same argument, stated for each reader in turn.

The salt's own creation is the one check-then-create the key-per-claim shape does not remove, and it is the same non-atomic read-modify-write this memo rejects for a list: two tabs that find no salt both generate one and both write it, the second write replaces the first, and the tab that lost the race holds a salt that no record of its own was salted with. `[unverified]` — an argument from what two `getItem`/`setItem` pairs on one key can interleave into, not a measurement.
Left as the paragraphs above state it, that race makes the guard fail open rather than merely lose a claim: the losing tab computes its invoice's digest with the salt it generated, so the record it writes is named by a digest that no other page — and no later page of this browser, which reads the salt the winning write left — can recompute. The invoice then reads as unclaimed on the next open, and the panel the record exists to refuse is offered again. `[unverified]` — the same argument, stated as the cost it is: a record whose digest cannot be recomputed answers nothing.
The behaviour that makes a lost race harmless is one rule about where the digest comes from, and it is stated as the claim's own steps because nothing in the storage API sequences them for us:
- A claim reads the salt, and if no salt is stored it generates 32 bytes and writes them under the salt's key; it never writes that key while a value is there, so one browser's storage is never left holding two candidate salts by a claim that can see the first.
- The digest is computed from the salt **read back after that write**, never from the value the claim generated, so a tab whose own write lost the race computes with whatever value the storage holds by then rather than with the bytes it drew; the verification below is what catches a value that changed again before that tab's key was written.
- The claim writes its own key, then reads both the salt and its own key back. A salt that still reads the value the digest was computed with leaves the claim as written; a salt that changed means the claim's key names a digest nothing can recompute, so the claim recomputes the digest with the read-back salt, writes that key, and removes the key it wrote under the other value.
- Verification is retried within a bound — the salt can only change while a claim is between its own writes, and it stops changing as soon as the writes that raced have landed — and a claim that cannot reach agreement is not recorded at all: this browser keeps the in-memory latch, the payer is told the attempt is remembered for this page only, and the panel is never opened as if nothing had happened.
`[unverified]` — a reading of what the two storage calls of each step leave when two tabs interleave them, not a measurement.
That rule buys the invariant the record needs: every record a reader can find was written under the one salt the storage holds when the claim was verified, whatever order two tabs interleaved, so no lost race strands a digest, and the only outcomes are a claim that can be read and a claim that was refused rather than written unreadably. `[unverified]` — a consequence of the steps above, not a measurement.
The orderings that still end the race are both benign: either both tabs read no salt and the later write wins with both claims computed under it, or a Forget in another tab removes the last record and the salt between the claim's read and its write, in which case the claim recreates a salt, is the only record under it, and is verified against it. `[unverified]` — the same argument, for each ordering in turn.
None of it needs a transaction, which is why the shape survives the API the memo already rejects a list under: no claim ever rewrites another claim's key, the salt's write is one that two tabs may both perform without a reader depending on which came first, and every decision a claim makes is taken from a value it read after writing rather than before. `[unverified]` — the same argument, stated as the reason no compare-and-swap is required.

Retention: keep at most 32 records for a bounded time — newest kept, oldest dropped, and a claim dropped once it has passed its expiry — and give the payer a Forget control that clears this browser's record for the invoice.
The two figures are part of the design rather than of whatever implements it: at most 32 records stand under the prefix once a retention pass has finished, and a claim expires on the UTC day 90 days after the day it was written, so everything the retention bound promises can be checked against a stated count and a stated number of days.
The count is stated over the state a pass leaves rather than over every instant, because two tabs' passes can run at the same moment: each counts the prefix and selects the lowest order to drop, both can select the same record, and the second write then leaves one record more than the cap until a pass reads the prefix back and drops one. `[unverified]` — an argument from what two read-modify-write passes over one prefix can interleave into, not a measurement.
Thirty-two is a whole number of ordinary sessions on one device and small enough to enumerate by hand, and 90 days is long enough that a payer who comes back to an unpaid invoice is still refused while the salt it costs is bounded by one quarter.
The expiry is what bounds the salt the record keeps: a count alone never falls to zero, because it keeps at least one record, so without an age bound one old claim would keep a random per-browser value for as long as the browser lives. `[unverified]` — an argument from how the count and the age bound between them decide what the storage holds, not a measurement.
The order a claim was made in is the one thing a claim reads before it writes, and it is recorded in the claim's own value: the highest order found under the prefix, plus one.
The record keeps at most that cap's worth of keys under its own prefix, counted by enumerating the keys the app itself wrote and dropping the lowest order among them, and it drops every key of that prefix whose expiry day has passed.
A pass is a repeat rather than one count and one drop: it enumerates the prefix after its own write, and while it finds more than 32 keys under it or any key whose expiry day has passed, it drops the lowest order among them and reads the prefix again, finishing on a read that finds neither. `[unverified]` — a consequence of counting after the write rather than before it, not a measurement.
The repeat is what makes the count a bound the storage holds rather than a figure one tab computed: the record two passes select is the same record whenever both enumerate the same prefix, so a tab that finds its selected key gone has to select again rather than count its intent as a drop, and only a read taken after every write can tell the two apart. `[unverified]` — the same argument.
It ends because the count cannot stand still while no claim writes: when two passes choose the same record, the first removal drops the count and the second finds its key gone, while the only step that raises the count is a claim's own write, which a claim performs once, so a fixed set of concurrent claims can raise it only a fixed number of times before a pass reads it at or below the cap. `[unverified]` — an argument from what each step adds and removes, not a measurement.
Retention therefore runs at two moments rather than only when a claim is made, and both are moments any run of the app reaches: the claim's own pass before it writes, and the lookup that decides whether to refuse a panel, before it answers.
The read-side pass is what makes the bounds hold on a device that has stopped being used for payments but is still opened: an expired record cannot refuse a panel it no longer bounds, cannot answer as a claim, and is not counted by the cap, whatever the storage still holds when the app starts. `[unverified]` — a consequence of the two moments, not a measurement.
The count cap and the age bound count records and nothing else, and the count keeps at least one of them: the salt is deleted by the rule stated below from the state of the record rather than by a bound of its own, so a bound that dropped the salt while it kept a record would strand that record's own digest, and a bound that dropped every record and left the salt would leave a per-browser value behind with nothing to protect.
The expiry day is stored coarsely, as one UTC day, and it is the one time value the record holds: a claim's age cannot be read from its order, and a stamp finer than the day would say when in the day a payment was attempted, which is more than the age bound needs.
What the write shape does make safe is the value a claim writes: a claim writes the key that names its own invoice and rewrites nothing another claim also writes, so two tabs claiming two different invoices at the same moment cannot overwrite each other's claim, which is the read-modify-write that loses a claim in one shared list. `[unverified]` — an argument from the shape of the key, not a measurement.
Retention is the one step that reads and writes the whole prefix, and interleaving it is not safe: a claim takes the highest order it finds plus one, so two claims made in the same moment can carry the same order, and the drop cannot order two equal ones with each other. `[unverified]` — an argument from how the cap counts and orders the keys, not a measurement.
That tie costs the two claims their order against each other rather than one of them a value when it is written: the pair carries the highest order found plus one, so it is the last thing the cap reaches and never the first — the drop takes the lowest orders, so no record just written is dropped while a record of a lower order stands below the cut. The cost appears later, when the cut falls between the two: with nothing to order them by, the drop takes whichever it enumerates first and keeps the other for a write longer, and the invoice whose record goes first then reads as unclaimed, so a panel reopened for it in this browser is not refused — the one failure the record exists to prevent, and the price of a cap that counts and orders keys no transaction protects. `[unverified]` — a reading of the cap's own rule, which drops the lowest order among the keys it finds, against the order a claim writes.
The collision costs no more than that: no record is invented, no other invoice's claim is overwritten, and the other claim of the pair still stands, while the cap's own drop of the oldest records remains the deliberate loss the cap states. `[unverified]` — the same argument, bounded.
The cap's own count is the other thing interleaving reaches, and the repeat above is what answers it: the second of two passes that selected the same record leaves the prefix one record above the cap, and its own next read is what drops one, so the count is a bound on the state a pass leaves rather than one the storage holds at every instant. `[unverified]` — the retention paragraph's argument, applied to the drop two passes share.
The salt follows the record's state and holds no retention of its own: it is a persistent per-browser identifier, so it may not outlive the records it salts, and its life is the life of the record — it stands while any claim stands, and the step that leaves no record under its prefix is the step that deletes it. `[unverified]` — a consequence of how the digest is computed, not a measurement.
Forget therefore clears both, in the one place the payer reaches it: the record for the invoice, and — when that was the last record the storage held — the salt with it, so the state the payer asked to forget leaves nothing behind that names this browser, and a fresh salt salts whatever is written next.
A salt cleared while records remain would strand them: the guard could no longer recompute their digests, so they would read as unclaimed and the payer would be paid-and-forgotten rather than protected, which is why the salt moves only with the last record it belongs to. `[unverified]` — the same argument.
The deletion rule is one rule rather than one per path, and it is stated in terms of the state both paths leave: the salt is deleted in the step that leaves no record under the record's prefix, and in no other step. `[unverified]` — the same consequence, stated so the cap and the salt cannot disagree.
Forget reaches that state when it clears the last record, and deletes the salt in the same step; the age bound reaches it in the retention pass that finds no record left under the prefix, and deletes the salt in that same step, which is what keeps the identifier from outliving the last claim by more than the expiry, measured from the first run of the app after the last claim's expiry day.
The count cap cannot reach it, because it keeps a fixed number of records and never fewer than one, so it always leaves a record to salt, and it deletes nothing but records.
So no step leaves this browser holding a random value of its own with nothing to salt, and no step deletes the salt from under a record it keeps: while any record stands the browser keeps one random value of its own, the step that removes the last record removes it, and no run of the app keeps or consults a record past its expiry day, so the random value lives for at most the expiry past the last claim this browser made, counted from the first run of the app after that day.
A device the app is never opened on again is the case neither bound reaches, and no design without a server reaches it: the storage an entry sits in has no expiry of its own, and an entry is removed only by a script or by the payer clearing site data, so nothing runs for a site nobody opens. `[reported from an external source]` — the Web Storage API of the HTML Standard, whose entries persist until a script or the user removes them and which schedules no expiry for them.
What the design can state instead is exactly that: no run of the app consults or keeps an expired record, the pass above removes it with the salt before the app answers anything, and on a device that is never opened again the record's bytes and the salt beside it stay where the browser put them until the payer clears them or the app runs again. `[unverified]` — a reading of what a bound stated over the app's own runs can promise, not a measurement.
The wording `README.md` gains must state the bound in those terms rather than as the record expiring by itself, and must state the count as the number of markers a finished retention pass leaves rather than as one the storage holds at every instant.

The Forget control cannot sit in the payment panel or in the refusal notice. `[verified in this repository]` — the refusal path builds no panel: `openPayPanel` reports the refusal through the notice region and builds no panel in `app/ts/ui/pay.ts`, the notice region is one text paragraph with no controls (`showNotice` in `app/ts/app/shell.ts`), and the notice interface offers only showing and clearing a notice (`app/ts/ui/notice.ts`).

The affordance would therefore sit in the payer's document actions — the region `documentActions` builds beside Pay and Save as PDF (`app/ts/ui/view.ts`) — shown only when this browser holds a record for the invoice, and the refusal's wording would name it there.

A later payer of the same invoice on a shared browser would be refused although they never attempted it: the refusal tests only whether the invoice's key is already claimed, not who claimed it. `[verified in this repository]` — the refusal is a lookup of the invoice's key in the attempted-payment record in `app/ts/ui/pay.ts`.

### What a Device-Side Guard Cannot Do

A guard on the payer's device cannot stop a determined double payment: another browser, a private window, cleared site data, or a second device never consults the record, because the record lives in one browser's storage and nowhere else. `[unverified]` — a consequence of the design, not a measurement.
The chain is the only authority, and this app cannot ask it, because `connect-src 'none'` means it reaches no node and the wallet's own report is all it sees. `[verified in this repository]` — `app/index.html`'s policy and the network sweep.
The guard's job is the ordinary accident, and the wording should say so.

## 5. A Plain-Language Note on Address Lengths

Address lengths look arbitrary and are not: four of these five are a fixed amount of address data spelled in an alphabet that ends in a checksum, so one mistyped character is caught before anything is paid, and the only thing that varies is how many characters the spelling takes; the unified container is the exception, because its length follows the list of receivers it carries rather than a fixed payload. `[verified in this repository]` — the five decoders named below, each of which bounds a paste's length before it decodes it.

- A Zcash transparent address (`t1…` or `t3…`) is 35 characters: 26 bytes of address data — a 2-byte version marker, a 20-byte hash, and a 4-byte checksum — spelled in Base58Check, the older Bitcoin-style alphabet, which needs no more than 36 characters for that data, so a longer paste is refused before it is decoded (the length bound in `app/ts/wallet/zcash-address.ts`). `[reported from an external source]` — the Zcash protocol specification's transparent-address encoding, whose 35-character count the module's 36-character decode bound admits without stating.
- A Zcash Sapling address (`zs1…`) is 78 characters: 43 bytes of key data — the diversifier and the payment key the address is built from — spelled in Bech32, the newer alphabet Zcash shares with Bitcoin, which carries a six-character checksum and spends more characters on the same bytes than the older one does (the data size in the same file). `[reported from an external source]` — the Zcash protocol specification's Sapling-address encoding, whose 78-character count the module's 90-character decode bound admits without stating.
- A Zcash TEX address (`tex1…`) is 42 characters: a 20-byte payload carrying the same hash a `t1…` address of the same script carries beside its version byte, spelled in Bech32m with a six-character checksum, so it names one script in the transparent-source-only spelling ZIP-320 defines rather than a second address (the length and the payload width in `app/ts/wallet/zcash-address.ts`). `[verified in this repository]` — the `tex` human-readable part, the 42-character length, and the 20-byte payload the module checks, beside ZIP-320, "Transparent-Source-Only Address", which defines that spelling and the part it carries.
- A Zcash unified address (`u1…`) runs to 311 characters — the widest-address bound in `app/ts/payment/schemes.ts`, derived as the widest symbol the app draws, less what a `zcash:` link spends besides the address, less a margin of 8 bytes.
- A Monero address is 95 characters, or 106 for an integrated one (the form table in `app/ts/wallet/monero-address.ts`).

The `zs1z7rejl…kngh9sly` example that circulates in write-ups about Zcash is not a valid Sapling address: it is 77 characters, one short of the 78 a mainnet one has, and `app/ts/wallet/zcash-address.ts` refuses it for that length rather than for its checksum. `[reported from an external source]` — zcash/zcash-blog issue #8, where such examples are confirmed not to be valid addresses; the 78-character count and the length refusal are the statement `app/ts/wallet/zcash-address.ts` makes, read in this repository.

Whether a wallet parses a `zcash:` payment link whose address is a TEX address is not established here: ZIP-321's address grammar predates ZIP-320, and its address validity requirement names only the transparent, Sapling, and unified forms. `[unverified]` — a reading of ZIP-321's address grammar against ZIP-320's later form, not a measurement, and no wallet was exercised for it.

A unified address is long because one string has to hold a list of the recipient's addresses — one for each form of address the recipient can receive — so a sender can pay whichever form that recipient supports. `[verified in this repository]` — the container-as-item-list grammar in `app/ts/wallet/zcash-address.ts`, and the 311-character bound in `app/ts/payment/schemes.ts`; the validator checks only that the container's data is long enough to be such a list, and never reads the addresses inside it.
That is normal, not a defect, and it is why the screen ladder and the print ladder exist. `[verified in this repository]` — the two ladders `FIT_RUNGS` publishes in `app/ts/ui/fit-value.ts`, one for the screen and one for print.
